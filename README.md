# 예제 3 · 약관 경계사례 탐지 및 테스트 케이스화 에이전트

약관 초안에서 **판정 기준이 모호하거나 문서 간에 다르게 정해진 지점**을 찾아,
업무로 넘길 수 있는 테스트 케이스로 구조화합니다.

지급 여부를 판정하는 도구가 아닙니다. 약관 작성 과정에서 놓친 사례를 드러내
약관 수정 검토로 넘기는 것이 목적입니다.

동봉된 `data/policy_sample.pdf`는 **교육 실습용 가상 약관**입니다.
실재하는 보험상품이나 보험회사와 관련이 없습니다.

> 윈도우 PowerShell에서는 경로 구분자가 `\` 입니다.
> `python src\run.py` 처럼 바꿔서 실행하세요.

---

## 실행

```bash
pip install -r requirements.txt

claude --version                                # CLI 확인
claude -p "테스트" --output-format text          # 로그인 확인

python src/parse_policy.py      # 1회만. work/clauses.json 생성
python src/run.py               # 에이전트 루프 실행
python src/score.py             # 심어둔 함정 대비 탐지율 채점
```

재실행 시에는 저장된 LLM 응답으로 재생할 수 있습니다.

```bash
python src/run.py --use-cache   # 모델 호출 0회, 동일한 실행을 재생
```

## 에이전트 워크플로

```
STEP 1  모호 표현 탐지                      (LLM)
STEP 2  Scenario Generator                  (LLM)
STEP 3  Coverage Critic                     (LLM)
          insufficient → 미충족 축 전달 → STEP 2 추가 생성
          기존 사례는 버리지 않고 누적. 최대 2회.
STEP 4  Adjudication Evidence Retriever     (코드, BM25 + Dense + RRF)
STEP 5  Case Critic                         (LLM)
STEP 6  Code Verify                         (코드)
          STEP 5 또는 6에서 반려
            → 반려 사유를 반영해 재생성
            → STEP 4 재검색 (시나리오가 바뀌면 근거도 다시 찾아야 한다)
            → STEP 5 → STEP 6
STEP 7  Test-case Formatter                 (코드)
STEP 8  Human Reviewer HTML                 (코드)
```

각 루프에 상한이 있습니다. 커버리지 추가 생성 2회, 사례별 재생성 2회,
처리 표현 수 5개, 목표 케이스 10건. 상한에 걸려 멈추는 것은 실패가 아니라
설계입니다.

## 왜 검토자가 넷인가

| 컴포넌트 | 보는 대상 | 보는 것 |
|---|---|---|
| Coverage Critic | 사례 **집합** | 판단 경계 축이 고루 덮였는가, 사례 유형이 한쪽에 쏠렸는가 |
| Case Critic | 사례 **하나** | 해석이 실제로 갈리는가, 근거가 결론을 뒷받침하는가 |
| Code Verify | 사례 **하나** | 확인 가능한 사실 — 조문 실재, 인용 일치, 날짜 형식, 금지 표현 |
| Human Reviewer | 최종 산출물 | 채택 여부 |

**Case Critic과 Code Verify는 일부 항목이 겹칩니다.** 인용 실재 여부와
해석 A/B 동일 여부를 양쪽에서 봅니다. 의도된 중복입니다.

겹치는 항목은 모두 "찾아보거나 계산하면 답이 나오는 것"입니다. 모델은
이런 것도 틀리고, Case Critic 역시 Generator와 같은 모델이라 같은 실수를
같이 합니다. 그래서 코드가 다시 봅니다. 실행 로그에서
`[Code Verify] ... REJECT ... ※ Case Critic은 통과시킴`이 찍히면
그 상황이 실제로 발생한 것입니다.

## 하이브리드 검색

BM25(키워드)와 Dense(의미)를 각각 돌린 뒤 RRF로 합칩니다. **기본 동작입니다.**

- BM25는 "관혈적", "제5조" 같은 정확한 용어와 조문번호에 강합니다.
  단어가 겹치지 않으면 못 찾습니다.
- Dense는 "보험금을 안 주는 경우"로 "면책사유"를 찾습니다.
  대신 희소 토큰을 놓칩니다.
- 점수 스케일이 다르므로 점수를 더하지 않고 **순위**로 합칩니다(RRF).

임베딩 모델은 코드에 박혀 있지 않습니다. 환경변수로 바꿉니다.

```bash
EMBED_MODEL=BAAI/bge-m3 python src/run.py     # 기본값
```

**모델 로드에 실패하면 조용히 BM25로 내려가지 않고 오류를 내고 멈춥니다.**
검색 품질이 달라진 것을 모른 채 결과를 믿게 되는 상황을 막기 위해서입니다.

`EMBED_BACKEND=fake`는 인덱스 캐시 로직의 단위시험 전용입니다.
의미 검색이 아니므로 실제 하이브리드 검증으로 쓰지 마세요.

### 두 가지 캐시는 서로 다른 것입니다

| | `--use-cache` | 임베딩 인덱스 |
|---|---|---|
| 저장 위치 | `work/cache.json` | `work/embed_index.npz` |
| 저장 대상 | LLM 응답 | 조각 임베딩 벡터 |
| 목적 | 동일 실행 재생 | 검색 전처리 재사용 |
| 무효화 | 사용자가 삭제 | `clauses.json` 해시 또는 모델명 변경 시 자동 |

`--use-cache`를 써도 검색은 매번 실제로 돕니다. 재생되는 것은 모델 응답뿐입니다.

## 판단 경계 축

`src/dimensions.py`에 정의되어 있습니다. **교안의 공식 목록이 아니라 이 약관을
읽고 정한 구현상의 설계입니다.** 다른 약관에는 맞지 않을 수 있습니다.

각 축은 실제 조항(`anchors`)에 연결됩니다. 연결이 하나도 확인되지 않는 축은
실행 시점에 제외되고, 제외 사실이 로그에 남습니다.

기간경계, 입원·재입원, 문서간충돌, 판정기준부재, 급부중복, 판단불가.

사례 유형은 별개의 축입니다. 정상사례, 경계사례, 반례, 판단불가.
전부 경계사례로 채우면 테스트 세트로 쓸 수 없으므로 Coverage Critic이
균형도 함께 봅니다.

## 산출물

| 파일 | 역할 |
|---|---|
| [`outputs/demo_output.html`](outputs/demo_output.html) | **Coverage/QA 실행 결과.** Coverage Gate 판정, 승인된 Test Case, 반려 사유를 보여줍니다. 브라우저로 엽니다 |
| [`outputs/edge_cases.html`](outputs/edge_cases.html) | **Human Review용 경계사례 목록.** Gate 결과와 무관하게 생존 사례를 카드로 보여줍니다. 승인된 Test Case가 아니라 검토 후보입니다. `python src/render_review.py`로 재실행 없이 다시 만들 수 있습니다 |
| `outputs/test_cases.json` | Formatter가 만든 구조화된 테스트 케이스. 후속 시스템용 |
| `outputs/edge_cases.json` | 검토 단계의 edge case 원본 기록 |
| `outputs/edge_cases.md` | 사람이 읽는 목록 |
| `outputs/rejected.json` | 반려된 사례와 사유, 반려 주체 |
| `work/loop_log.jsonl` | 루프가 돈 흔적. 한 줄이 독립 JSON 객체라 실행 중 append 가능 |

테스트 케이스는 날짜, 계약상태, 사고원인, 급부코드를 시나리오 문장 안에
두지 않고 별도 필드로 분리합니다. 그래야 UAT나 지급심사 검토로 넘길 때
사람이 다시 뜯어내지 않습니다. 약관에서 확인할 수 없는 값은 지어내지 않고
`"미확인"`으로 둡니다.

**기대결과는 항상 `"검토 필요"`입니다.** 지급/부지급을 확정하지 않습니다.
SKILL.md가 금지하고, `verify.py`가 문자열로 다시 막습니다. 약관만으로 결론이
나지 않는 사례는 `판단불가` 유형으로 보존합니다.

### HTML 산출물

두 파일은 중복이 아닙니다. `demo_output.html`은 Agent의 Coverage/QA 상태를,
`edge_cases.html`은 Human Reviewer가 실제 사례를 검토하는 화면을 보여줍니다.

- `outputs/demo_output.html` — Coverage/QA 결과
  - `test_cases`를 입력으로 씁니다.
  - Coverage Gate 결과에 따라 Test Case 생성이 차단될 수 있습니다.
  - 이번 실행은 `INSUFFICIENT_COVERAGE`로 차단되어 Test Case 카드 없이
    Coverage 판정과 반려 결과만 보여줍니다.
- `outputs/edge_cases.html` — Human Review용
  - Gate를 거친 `test_cases`가 아니라, 검증 과정에서 살아남은 `passed` 사례를 씁니다.
  - 사례마다 시나리오, 해석 A/B, 근거, 영향, 권고를 사람이 검토합니다.
  - 여기 실린 사례는 보험금 지급 판단이나 승인된 Test Case가 아니라
    약관 수정·검토를 위한 후보입니다.

## 1. 목적

Example 03에는 LLM 컴포넌트가 네 개 있습니다. **모호 표현 탐지 → Scenario Generator → Coverage Critic → Case Critic.** 프롬프트 설계 목표는 세 가지입니다.

1. **판정하지 않는다.** 지급/부지급 결론을 내지 않는다. 약관 문언이 두 가지로 읽히는 지점을 드러내 검토로 넘긴다.
2. **테스트 세트로 쓸 수 있게 만든다.** 경계사례만 모으지 않고 정상사례·반례·판단불가를 섞는다. 날짜·계약상태 같은 사실은 별도 필드로 분리한다.
3. **근거를 검증할 수 있게 만든다.** 실제로 있는 조문만 인용하고, 코드(`verify.py`)가 다시 확인할 수 있는 형식으로 낸다.

## 2. Initial Prompt

### V0

**Prompt status:** Reconstructed Implementation Instruction (구현 지시문) · 모델 입력 원문은 Actual

**Prompt**

**Reconstructed Implementation Instruction.** 실제로 입력한 문장이 아닙니다. 초기 코드·SKILL.md(`예제03_경계사례.zip`)와 V0 실행 기록을 보고 역으로 적었습니다.

```text
[목적]
보험 약관 초안에서 판정 기준이 모호하거나 문서 간에 다르게 정해진 지점을 찾아내는 에이전트를 만들어줘.
지급 여부를 판정하는 도구가 아니야. 약관 작성 과정에서 놓친 사례를 드러내 약관 수정 검토로 넘기는 것이 목적이야.

[입력]
- data/약관자료.pdf (교육용 가상 약관: 보통약관 + 특약 5종 + 별표 3종)
- parse_policy.py로 관·조·항·호 단위로 파싱해 work/clauses.json에 저장 (1회 실행)
- 각 조각은 "문서 > 관 > 조 > 항" 경로를 함께 가진다. 별표의 표는 표 구조 그대로 추출

[워크플로]
1. 모호 표현 탐지 (LLM) — 판정에 쓰이는데 정의되지 않은 표현, 문서 간에 다르게 정해진 지점
2. 관련 조문 검색 (코드) — BM25 기본. sentence-transformers가 있으면 임베딩 검색을 RRF로 결합 (--dense)
3. 생성 에이전트 (LLM) — 표현당 해석이 갈리는 사례 최대 2건
4. 비평 에이전트 (LLM) — 생성 과정은 보지 않고 결과물만 보고 반려 사유를 찾는다
   확인 항목: 해석 A/B가 실제로 다른 결론인가, 시나리오에 날짜·일수가 있는가,
   인용 원문이 조문에 실제로 있는가, 지급 여부 결론을 내리지 않았는가, 근거보다 결론이 과장되지 않았는가
5. 코드 검증 (verify.py) — 조문 실재, 인용문 원문 일치, 결론 표현 문자열, 시나리오 수치 포함 여부
   - 4 또는 5에서 반려되면 반려 사유를 반영해 재생성. 표현당 재시도 2회
처리 표현 수 제한, 목표 건수 도달 시 종료. 한도에 걸려 멈추는 것은 실패가 아니라 설계로 처리해.
```

V3에서 인용 문제는 줄었지만, 정상사례와 반례가 검증을 통과하지 못했습니다. 정상사례 지시("어느 쪽이 우세한지 밝혀라")와 Case Critic 1번 기준("해석A와 해석B가 실제로 서로 다른 결론인가")이 서로 부딪히기 때문입니다. 현재 Case Critic은 모든 유형을 경계사례 기준으로 심사합니다. 그래서 다음 개선이 필요합니다.

```text
[목적]
보험 약관 초안에서 판정 기준이 모호하거나 문서 간에 다르게 정해진 지점을 찾아,
약관 수정 검토로 넘길 수 있는 테스트 케이스로 구조화하는 에이전트를 만들어줘.
지급 여부를 판정하는 도구가 아니야. 약관 작성 과정에서 놓친 사례를 드러내는 것이 목적이야.

[입력]
- data/policy_sample.pdf (교육용 가상 약관)
- parse_policy.py로 조문 단위로 파싱해 work/clauses.json에 저장 (1회 실행)

[워크플로]
1. 모호 표현 탐지 (LLM) — 처리 표현 최대 5개
2. Scenario Generator (LLM) — 표현별 사례 생성
3. Coverage Critic (LLM) — 사례 집합이 판단 경계 축을 고루 덮는지, 사례 유형이 쏠렸는지 평가
   - insufficient면 미충족 축을 전달해 2단계에서 추가 생성. 기존 사례는 누적. 최대 2회
4. Evidence Retriever (코드) — BM25 + Dense 하이브리드 검색, RRF로 순위 결합
5. Case Critic (LLM) — 사례 하나씩: 해석이 실제로 갈리는지, 근거가 결론을 뒷받침하는지
6. Code Verify (코드) — 조문 실재, 인용 일치, 날짜 형식, 금지 표현 확인
   - 5 또는 6에서 반려 시: 반려 사유 반영해 재생성 → 4단계 재검색 → 5 → 6. 사례별 최대 2회
7. Test-case Formatter (코드)
8. Human Reviewer용 HTML 생성 (코드)
목표 케이스 10건. 상한에 걸려 멈추는 것은 실패가 아니라 설계로 처리해.

[검토 구조]
Case Critic과 Code Verify는 인용 실재 여부, 해석 A/B 동일 여부를 의도적으로 중복 확인해.
Case Critic도 Generator와 같은 모델이라 같은 실수를 할 수 있으니,
찾아보거나 계산하면 답이 나오는 항목은 코드가 다시 봐야 해.
Case Critic은 통과시켰는데 Code Verify가 반려한 경우 로그에 따로 표시해줘.

[검색]
- 임베딩 모델은 환경변수 EMBED_MODEL로 지정 (기본 BAAI/bge-m3)
- 모델 로드 실패 시 BM25로 조용히 내려가지 말고 오류 내고 멈출 것
- 임베딩 인덱스는 clauses.json 해시나 모델명이 바뀌면 자동 무효화

[판단 경계 축] (src/dimensions.py)
기간경계, 입원·재입원, 문서간충돌, 판정기준부재, 급부중복, 판단불가.
각 축은 실제 조항(anchors)에 연결하고, 연결이 확인되지 않는 축은 제외 후 로그에 남겨.
사례 유형(정상사례, 경계사례, 반례, 판단불가)은 별도 축으로 균형을 봐.

[출력 규칙]
- 날짜, 계약상태, 사고원인, 급부코드는 시나리오 문장에서 분리해 별도 필드로

- 기대결과는 항상 "검토 필요". 지급/부지급 확정 금지 (SKILL.md 규칙 + verify.py 문자열 검사)
- 약관만으로 결론이 나지 않는 사례는 판단불가 유형으로 보존

[재현성]
--use-cache 옵션으로 LLM 응답을 캐시해 동일 실행을 재생할 수 있게 해줘.
검색은 캐시 사용 시에도 매번 실제로 수행해.
```
